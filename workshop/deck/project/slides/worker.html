Step 2 · §4.6 · long jobs

A two-minute job runs beside the request, and streams its progress

Open-source app

A worker process claims queued jobs from the database:

select_for_update(skip_locked=True)

Two workers never take the same job.

Inside DrNext Academy

A background thread per job; its events stream to the screen as NDJSON, one line per update. A job whose server restarted is marked failed after 10 minutes.

Why no Celery? Each job is one streamed agentic run of 1–2 minutes: a queue service would add a moving part without adding value. Celery is the next step if jobs grow.

47:00–48:00. A web request must answer in seconds; a proposal takes 1–2 minutes. So the job runs in the background and the page follows it. Two valid designs for two contexts: the standalone app uses a database-polled worker; DrNext Academy runs the job in a thread and streams events, the same pattern its agent already uses.
